OrchardScout: exploring an orchard of unknown size with one camera

Dhruv Sharma · proof of concept, November 2026 · code, video and every run: github.com/dhruuvsharma/OrchardScout

Task

A drone flies under the canopy of a simulated orchard. Using only an RGB camera it must localise itself, explore, build a map and work out how big the orchard is (rows, row length, spacing, extent), which it is never told. Every run draws a new orchard (4–20 rows, 20–120 m long, random row and tree spacing, missing trees, jitter) and starts the drone in an alley or outside an edge, facing anywhere. Simulator ground truth only scores the run. One stated prior: the flight controller holds a known height (1.0 m), which fixes monocular scale. No IMU, GPS or depth sensor.

Method

  • Depth: Depth Anything V2 (metric) is ~5× off in scale at drone height; each frame it is rescaled so a RANSAC ground plane (bottom 12 % of the image) sits 1.0 m below the camera. Sky, depth-edge ramps and "rising" open-field ground are masked.
  • Visual odometry: KLT tracks + PnP/RANSAC on keyframe depth; the ground plane fixes roll, pitch and height every frame.
  • Mapping: occupancy grid (free space along every ray) and trunk landmarks (vertical point clusters within 5 m, corrected for seeing only the trunk's front).
  • Drift correction from orchard structure: a row compass (rows are parallel: RANSAC lines of trees hold the heading), a row lattice (rows are evenly spaced: the sideways position is corrected modulo the spacing) and landmark re-sighting.
  • Size: rows = density peaks across the row direction; spacings from trunks seen within 4 m (accurate depth) over a few seconds; width = (rows−1)×spacing.
  • Exploration: frontier-based (Dijkstra on an inflated grid). Only frontiers near mapped trees count, so open field beyond the edges is ignored and the run stops by itself once the orchard has been seen. Paths prefer alleys (depth is poor over open grass); a safety layer keeps clear of trunks.

What I learned

  • Monocular depth fails in structured ways: wrong global scale, compression with distance, open grass bent upwards. Masks, range limits and close-range measurements beat trying to "correct" it.
  • Most drift comes from turns at the orchard edge, facing open field. The orchard's own geometry (parallel, evenly spaced rows) is a strong, cheap prior that removes most of it.
  • A noisy correction can be worse than none: a heading fitted from a few trees random-walked; robust line fits fixed it.

Results: autonomous runs, each on a new orchard

Final code. Held-out: ten orchards (two rounds of five) never run before the code was frozen; an earlier held-out round found two failures, since fixed, and its orchards joined the development set. Camera: the real system. Perfect: simulator depth and pose (upper bound). Red: wrong row count.

Limitations and next steps

  • Simulation only (MuJoCo; Isaac Sim needs an RTX GPU). Next: Isaac Lab / PX4 and real orchard footage.
  • Failures, camera only: on the largest orchards (0.9–1.6 km of flight) drift near the edges passed half a row spacing and added or dropped edge rows (large #1, #2, #3): no loop closure yet, and re-seen rows are the natural constraint. A 7–11 % short spacing in wide alleys added a row (small #3, medium #3, medium #7). One run livelocked beside a trunk (now ended by a watchdog); its re-run touched a tree for 10 s. Perfect sensing: one run stopped early (free space is mapped to 8 m, trunks to 5 m). A revised explorer, run on all 21 orchards afterwards, had none of these exploration failures in 42 runs and the same camera-only row count (15 of 21): the limit now is drift and depth, not exploration.
  • Exploration is classical. Next: a learned exploration policy against this baseline, and an adversarial "environment agent" that generates orchards (lighting, fog, irregular rows, slopes) to find where camera-only navigation breaks.
